# MVVM with Katana

A worked example of the Model–View–ViewModel pattern wired through Katana's container. The source lives in [`Sources/Example/`](../Sources/Example) and ships as its own SPM target.

```bash
swift run Example                 # console driver
swift test --filter ExampleTests  # 19 Swift Testing cases
```

## Project layout

```
Sources/Example/
  Logger.swift              # cross-cutting dependency, non-final so it can be spied on
  Domain.swift              # Todo model + actor-based repository
  TodoListViewModel.swift   # @MainActor @Observable view model
  Modules.swift             # @Module enums grouping types per layer
  Composition.swift         # @Container App — the only place that aggregates modules
  ContentView.swift         # SwiftUI view using bare @Inject
  main.swift                # console driver
Tests/ExampleTests/
  ExampleTests.swift        # @TestContainer TestApp at a custom scope + 19 wiring/behaviour/override/cycle/named-binding tests
```

## Layers

| Layer       | Type                                          | Scope     | Sendable strategy           |
|-------------|-----------------------------------------------|-----------|-----------------------------|
| Model       | `Todo` (struct)                               | n/a       | implicit (Sendable fields)  |
| Service     | `Logger` (class)                              | singleton | `@unchecked Sendable`       |
| Repository  | `TodoRepository` (actor)                      | singleton | implicit (`actor`)          |
| ViewModel   | `TodoListViewModel` (`@MainActor @Observable`) | singleton | implicit (`@MainActor`)     |
| View        | `ContentView` / `TodoListScreen` (SwiftUI)    | n/a       | observes view model         |

Types are split across small `@Module` enums (one per layer), then aggregated by a single `@Container` annotation. SwiftUI views read dependencies through the framework-level `@Inject` wrapper — compile-checked against the registered type list, so a refactor that drops a registration breaks every dependent call site at build time.

## 1. Model

A plain value type:

```swift
struct Todo: Sendable, Identifiable {
    let id: UUID
    var title: String
    var isCompleted: Bool
}
```

## 2. Repository (actor → singleton)

Modelling the repository as an `actor` means:

- It's implicitly `Sendable`, so singleton scope works with no annotations.
- State mutation is serialised by the actor — no locks, no `@unchecked`.

```swift
@Injectable
actor TodoRepository {
    private var storage: [Todo] = []
    private let logger: Logger

    init(logger: Logger) { self.logger = logger }

    func all() -> [Todo] { storage }
    @discardableResult func add(title: String) -> Todo { … }
    func toggle(_ id: UUID) { … }
}
```

`@Injectable` synthesises the `Injectable` conformance, resolving `logger` through the container automatically.

## 3. ViewModel (`@MainActor @Observable` → singleton)

Three macros stack here, each with a single concern:

```swift
@available(macOS 14, iOS 17, *)
@MainActor
@Observable
@Injectable
final class TodoListViewModel {
    private let repository: TodoRepository
    private let logger: Logger

    var todos: [Todo] = []
    var isLoading: Bool = false

    init(repository: TodoRepository, logger: Logger) { … }

    func load() async { … }
    func add(title: String) async { … }
    func toggle(_ id: UUID) async { … }
}
```

- **`@MainActor`** — UI state mutation stays on the main thread. Also makes the class implicitly `Sendable`, satisfying singleton scope's `Sendable` requirement without explicit conformance.
- **`@Observable`** — SwiftUI tracks property reads and re-renders only the views that touched changed state.
- **`@Injectable`** — wiring; the macro reads `init` and generates resolution against the container.

The `nonisolated async` resolver generated by `@Injectable` calls the `@MainActor` initialiser via `await`, so the cross-actor hop is automatic.

## 4. Modules — `@Module` per layer

```swift
@Module(Logger.self)
enum ServiceModule {}

@Module(TodoRepository.self)
enum RepositoryModule {}

@available(macOS 14, iOS 17, *)
@Module(TodoListViewModel.self)
enum ViewModelModule {}
```

`@Module` emits a `static let types` array and a `KatanaModule` conformance. Splitting by layer keeps responsibilities clear and lets feature teams own their own modules — but a tiny app can just declare one aggregate `@Module(...)` enum if it prefers.

## 5. Composition root — `@Container(modules:)`

The dependency graph is **one declaration**:

```swift
@available(macOS 14, iOS 17, *)
@Container(modules: [
    ServiceModule.self,
    RepositoryModule.self,
    ViewModelModule.self,
])
final class App {}
```

The `KatanaCodegen` build plugin reads the module list, aggregates the types, validates scope uniqueness, and emits on `App`:

- **`init(_ customize:) async`** — builds the inner `Container`, registers each type, runs an optional override closure (used by tests).
- **`resolve(_:) async`** — one overload per registered type. Resolving an unregistered type is a compile error ("no matching overload"). Refactor-safe by construction.
- **`struct Snapshot: Resolver`** — sync, `Sendable`, typed. One stored property per registered type, plus typed `resolve(_:)` overloads. `App.Snapshot` is what SwiftUI consumes.
- **`snapshot() async -> Snapshot`** — eagerly resolves every singleton into the typed snapshot at app launch.
- **`EnvironmentValues.katanaDefault`** — the typed env slot the snapshot is installed into.
- **`View.katana(_ snapshot: App.Snapshot) -> some View`** — install modifier overloaded by snapshot type so multi-graph apps don't collide.
- **`extension Inject { init() }`** — bare `@Inject` init that reads `\.katanaDefault`. Plugin emits this only when exactly one container binds to `.default`.

```swift
let app = await App()
let vm = await app.resolve(TodoListViewModel.self)   // compile-checked
let snap = await app.snapshot()                       // App.Snapshot
```

Because the view model is singleton-scoped, every view that reads it gets the same instance, and `@Observable` keeps them all in sync.

> **Plugin required.** Every target using `@Container` must enable `KatanaCodegenPlugin` in `Package.swift`:
> ```swift
> .executableTarget(
>     name: "Example",
>     dependencies: ["Katana"],
>     plugins: ["KatanaCodegenPlugin"]
> )
> ```

## 6. SwiftUI view — bare `@Inject`, the Hilt equivalent

On Android Compose, Hilt lets a composable write `val vm: TodoListViewModel = hiltViewModel()` and get the view model handed over. Katana ships the same shape via the framework-level **`@Inject`** wrapper plus a single **`App.Snapshot`** installed at the composition root.

```swift
@available(macOS 14, iOS 17, *)
struct ContentView: View {
    @Inject var viewModel: TodoListViewModel    // ← bare, default scope
    @State private var draft: String = ""

    var body: some View {
        VStack {
            HStack {
                TextField("New todo…", text: $draft)
                Button("Add") {
                    let title = draft; draft = ""
                    Task { await viewModel.add(title: title) }
                }
            }
            List(viewModel.todos) { todo in
                HStack {
                    Image(systemName: todo.isCompleted ? "checkmark.circle.fill" : "circle")
                    Text(todo.title)
                }
                .onTapGesture { Task { await viewModel.toggle(todo.id) } }
            }
        }
        .task { await viewModel.load() }
    }
}
```

`ContentView` never mentions `Container`, never calls `resolve`, never takes the view model through `init`. If you delete `TodoListViewModel` from `ViewModelModule` (or remove the module from `@Container(modules:)`), **every `@Inject var x: TodoListViewModel` in the codebase stops compiling** — exactly the refactor safety the macro is for.

### Where does the resolution happen?

**Once**, at the composition root. The `@main` app passes the graph type to `.katana(...)`; the framework handles construction, snapshot, and environment install:

```swift
@main
struct ExampleApp: SwiftUI.App {
    var body: some Scene {
        WindowGroup {
            ContentView().katana(App.self)
        }
    }
}
```

> **Naming note**: this guide uses `App` for the `@Container` class to match the existing `Sources/Example/` code. In a real SwiftUI app where the `@main` struct conforms to `SwiftUI.App`, the bare `App` name collides — use `AppGraph` / `AppContainer` / `Composition` for your `@Container` class to avoid ambiguity. See [`modules.md`](modules.md#naming).

**100 view models? Still one `.katana(...)` call.** Each descendant view writes `@Inject var x: SomeViewModel` — no per-type environment plumbing, no prop-drilling, no service location.

### How it works (and why `@Observable` tracking still fires)

`App.Snapshot` is a `Sendable` struct with one stored property per registered type. The plugin emits typed `resolve(_:)` overloads so the compiler picks the right return type at the call site. `@Inject`'s bare `init()` (plugin-emitted) reads `\.katanaDefault` from the environment; `Inject.wrappedValue` calls `snapshot.resolve(Value.self)` — the resolved value is the same instance the container holds, so SwiftUI's Observation framework still tracks property reads on the `@Observable` view model. Binding mechanism doesn't matter; property access does.

| Concern                              | Katana solution                                                                       |
|--------------------------------------|---------------------------------------------------------------------------------------|
| Async container, sync views          | `App.snapshot()` → typed sync `App.Snapshot` built once at launch                     |
| Scaling to N view models             | One `.katana(...)` install; per-view `@Inject` reads any registered type              |
| Refactor catches drop-registration  | Deleting a type from a `@Module` breaks every `resolve` / `@Inject` site              |
| Avoiding service location            | Views declare types; never touch `Container`                                          |
| `@Observable` re-renders             | Resolved value is the live singleton; observation hooks on property reads             |
| Tests                                | `@TestContainer TestApp` mirrors the production graph with override-first ergonomics  |

## 7. Testing — `@TestContainer`

`@TestContainer` is the test-target peer of `@Container`. Same shape, same compile-time safety, plus override-first ergonomics and a `TestContainerMarker` conformance for project lint.

The plugin scans per target, so the test target re-declares its own modules. Aggregated into a single test module for brevity:

```swift
// Tests/ExampleTests/ExampleTests.swift
@testable import Example

@available(macOS 14, iOS 17, *)
@Module(Logger.self, TodoRepository.self, TodoListViewModel.self)
enum TestAppModule {}

@Scope
enum ExampleTestsScope { case test }

@available(macOS 14, iOS 17, *)
@TestContainer(scope: .test, modules: [TestAppModule.self])
final class TestApp {}
```

> The custom `.test` scope avoids a collision with `Example.App`'s `.default` scope when the test target uses `@testable import` — both targets would otherwise extend `EnvironmentValues` with the same `katanaDefault` property. Using `.test` for the test container sidesteps that.

### Resolving the real graph

```swift
@Test func resolvesViewModelFromTestApp() async throws {
    let app = await TestApp()
    let viewModel = await app.resolve(TodoListViewModel.self)
    await viewModel.load()
    #expect(viewModel.todos.isEmpty)
}
```

`app.resolve(SomeUnregisteredType.self)` is a **compile error** — same overload-based safety as `App`.

### Override via the closure init

The most common shape: build the graph with overrides applied during construction.

```swift
@Test func overrideRepositoryPreseedsStateViaClosure() async throws {
    let app = await TestApp { c in
        await c.override(TodoRepository.self) { container in
            let logger = await container.resolve(Logger.self)
            let repo = TodoRepository(logger: logger)
            await repo.add(title: "Seed A")
            await repo.add(title: "Seed B")
            return repo
        }
    }

    let viewModel = await app.resolve(TodoListViewModel.self)
    await viewModel.load()
    let titles = viewModel.todos.map { $0.title }
    #expect(titles == ["Seed A", "Seed B"])
}
```

### Override post-construction

`@TestContainer` adds `override(_:with:) async` and `override(_:factory:) async` directly on the class — useful when you want the production graph first, then swap one dep for a particular assertion.

```swift
final class SpyLogger: Logger, @unchecked Sendable {
    private let lock = NSLock()
    private var _captured: [String] = []
    required init() { super.init() }
    var captured: [String] { lock.lock(); defer { lock.unlock() }; return _captured }
    override func log(_ msg: String) { lock.lock(); defer { lock.unlock() }; _captured.append(msg) }
}

@Test func overrideLoggerPostConstruction() async throws {
    let app = await TestApp()
    let spy = SpyLogger()
    await app.override(Logger.self, with: spy)

    let viewModel = await app.resolve(TodoListViewModel.self)
    await viewModel.add(title: "logged")
    #expect(spy.captured.contains { $0.contains("logged") })
}
```

`override(_:with:)` clears any cached singleton, so it takes effect even if the type was already resolved before the override.

### Independence per test

Each test constructs its own `TestApp`. Singleton scope is **per instance**, not global — there's no shared state to reset between tests.

```swift
@Test func twoAppsAreFullyIndependent() async throws {
    let appA = await TestApp()
    let appB = await TestApp()
    let vmA = await appA.resolve(TodoListViewModel.self)
    let vmB = await appB.resolve(TodoListViewModel.self)
    await vmA.add(title: "Only in A")
    #expect(vmA !== vmB)
    #expect(vmB.todos.isEmpty)
}
```

### Why `@TestContainer` and not just `@Container`-in-tests

Both work mechanically. `@TestContainer` is its own attribute for four reasons:

1. **Discoverability** — `@TestContainer` shows up next to `@Test` in autocomplete.
2. **Marker conformance** — `TestContainerMarker` lets project lint enforce "no test containers outside `Tests/`".
3. **Test-only API surface** — post-construction `override(_:with:)` only makes sense in tests; keeping it off `@Container` keeps production small.
4. **Future room** — resolution logging, snapshot/spy mode toggles, XCTest hooks can land here without polluting `@Container`.

## Why singleton for the view model?

This example treats the list view model as app-wide state. Per-screen detail view models that take instance data (e.g. a selected `Todo.ID`) should be **transient** so each screen gets its own copy:

```swift
@available(macOS 14, iOS 17, *)
@MainActor
@Observable
@Injectable(scope: .transient)
final class TodoDetailViewModel { … }
```

Transient scope hands ownership across the actor boundary via `sending`, so the type does not need to be `Sendable`.
